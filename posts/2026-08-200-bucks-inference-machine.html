200 Bucks Inference Machine

A local LLM inference server built on secondhand mining hardware, running full GPU-resident inference for around $200 in parts. Updated September 2026: down to one card, new model, and first KV-cache experiments.

119 s → 0.3 s Time to first token on a 15.6k-token prompt, restoring a saved KV cache snapshot 95% precision Gemma 4 E4B on 78 hand-labeled documents, ahead of three Qwen models including an 8B −46% load time Soldered AC coupling capacitors onto the PCIe lanes to unlock x16 ~10× throughput Prompt processing from 18 to 190 tokens/s after finding a stuck 300 MHz clock cap

Overview

This project turns a Huananzhi X99 BD4 motherboard and two CMP 40HX mining GPUs into a working inference box. The goal was privacy first: proprietary GPU board schematics purchased for a separate repair project should never be sent to an external LLM API, so the only real option was to build something local and capable enough to run a real model at usable context length.

Hardware

The board is a Huananzhi X99 BD4, originally paired with two CMP 40HX cards (TU106, compute capability sm_75, 8GB VRAM each). One of the two cards has since died, so the machine now runs on a single 8GB card, with only 7.7GB of system RAM next to it. Everything below was sized around that. CMP cards ship without display output and with reduced driver support since they were designed for mining, not compute workloads, so getting them recognized properly took some work.

One of the bigger hardware fixes was a PCIe lane negotiation issue. The cards were not initially negotiating full x16, which capped throughput. AC coupling capacitors soldered directly onto the PCIe lanes resolved this and unlocked full x16 negotiation on both cards. Measured on this machine, model load time dropped 46%.

Idle power draw is managed with a systemd service, cap-cmp40hx.service, that locks GPU clocks to 300 MHz when the cards are not in use, bringing idle draw down to around 12 to 15 watts. Before running inference, clocks need to be manually reset with nvidia-smi -rgc, otherwise the locked clock caps performance.

Forgetting that step is expensive. In one session the GPU showed 100% utilization but sat at 300 MHz and 35W, processing prompts at about 18 tokens per second. Once the clock came up to 1935 MHz, the same work ran at about 190 tokens per second, roughly 10x faster. A 15.6k-token agent prompt went from an estimated 17 minutes before the first token to about 80 seconds. nvidia-smi dmon -s uc is the quick check: if pclk reads 300 under load, the cap is still on.

Software stack

Inference runs through mistral.rs, built from the GitHub master branch rather than the published 0.8.1 crate, which had a linking bug in afq.cu that prevented a clean build.

Getting the CMP cards working with a modern CUDA toolchain required a small patch to candle kernels, specifically compatibility.cuh. The original guard caused a redefinition collision between hmax_nan and hmin_nan on this hardware. Changing the guard condition to check both CUDA_ARCH under 800 and CUDART_VERSION under 12080 resolved it.

The server originally ran qwen3:8b through mistral.rs behind an OpenAI-compatible endpoint, with context tuned to 32,768 tokens so the model and context stayed resident across the two 8GB cards.

With one card left, it now serves Gemma 4 E4B through Ollama (llama.cpp). An 8B model plus a useful context no longer fits in 8GB, and Gemma 4 E4B suits the constraint well. About 4B parameters are active, and a large per-layer embedding table stays in system RAM instead of VRAM. Most layers use sliding-window attention, so its KV cache is small: the full 131k context costs about 2GB. Measured on this card with the clock up: about 220 tokens per second of prompt processing and 36 tokens per second of generation.

Picking it wasn't a guess. I benchmarked it against Qwen3.5 4B, Qwen3 8B and Qwen2.5 3B on a structured extraction task, and it beat all three on precision, including the model twice its size. Full write-up with charts.

What it powers

The machine first hosted OpenClaw, a personal agent for email triage, calendar management, and job application tracking. That turned out to be a poor fit for one small card. OpenClaw sends a ~15.6k-token system prompt on every agent step, and llama.cpp couldn't reuse its cache between steps on Gemma's sliding-window layers. So each step paid about 80 seconds of prompt processing before producing anything, and the agent's own watchdog aborted runs when the clock was stuck.

I dropped the agent and gave the model a narrower job it does well: schema-constrained extraction. It reads a document, fills a fixed JSON schema, and backs each claim with a verbatim quote that ordinary code checks against the source. The model extracts facts; code decides what to do with them.

KV cache snapshots

That 80-second prompt cost is the problem I'm now working on directly. llama-server can save a slot's KV cache to disk and restore it later. So a long shared prefix could be processed once and reloaded in milliseconds, instead of being recomputed on every request. The first experiment, on a 15,600-token prefix:

Gemma 4 E4B, defaultGemma 4 E4B, --swa-fullQwen2.5 3B, default
Cold time to first token85 s119 s83 s
Warm time to first token (restore + new tokens)85.6 s (restore discarded)0.29–0.34 s0.44–0.45 s
Snapshot on disk264 MiB264 MiB549 MiB
Restore time169 ms169 ms280–300 ms

On a normal full-attention model (Qwen2.5 3B) it works out of the box. Gemma is harder: its sliding-window layers keep only the last ~1,024 tokens in a ring buffer, and after a restore the server logs forcing full prompt re-processing ... (likely due to SWA) and throws the cache away. With --swa-full (sliding-window layers keep their full history) the restore holds and time to first token falls from 119 s to 0.3 s. That costs 1.3GB more VRAM at 32k context and slower cold runs. Part of the cold-run gap may be the GPU clock, which I haven't separated out yet.

The next step is a C++ proxy in front of llama-server that treats these snapshots like a small storage engine. It will hash prompt prefixes into a radix tree, keep content-addressed snapshot files with an append-only index, tier them between RAM and SSD, and evict by recompute cost against size. The open question is whether saving just the sliding-window state at the prefix boundary can avoid --swa-full entirely.

Community context

CMP mining cards are a known genre of budget hardware experimentation, mostly documented outside English-language sources. Two references shaped how this build was approached.

A Bilibili video from the channel 吃饭团的佳乐同学, part of a long running series on modded mining cards, benchmarks a modded 40HX against an RTX 2060 Super and RTX 2060. Their numbers put theoretical performance at least 10 percent ahead of the 2060 Super, with gaming performance about 20 percent behind the 2060 Super but 7 percent ahead of the plain 2060, and productivity or video editing work landing close to the 2060 Super. Deep learning performance was left unverified in that video, which is part of why this project exists as its own writeup.

A more directly relevant source is a Habr article by Oleg titled "Dark horses of AI," covering LLM inference specifically on the CMP 40HX, 50HX, and 90HX line. It confirms the same pattern seen in this build: synthetic FP32 benchmarks make these cards look ten times slower than older gaming GPUs, but real LLM inference throughput lands close to an RTX 2060 or 3060, around 30 tokens per second on 8B models. The article traces this to Ollama and similar frameworks running inference primarily in FP16 rather than FP32, and FP16 throughput on these cards is nowhere near as crippled as FP32 is, in some cases beating an RTX 3060 outright.

The article also independently confirms the PCIe capacitor fix used on this build. Mining cards typically ship with capacitors populated only for 4 lanes even though the board supports 16, and soldering 0402 package 100 or 220 nanofarad capacitors onto the remaining lanes physically unlocks the missing width. Their testing found that lane width barely affects raw token throughput, roughly a percent or two gain from 4 lanes to 16, since 8 lanes already clears the bottleneck for inference. The real benefit is model and context load time, which improved by close to half going from 4 lanes to 16 in their tests. That lines up with why this build targeted full x16 negotiation — the win is in how fast the server comes up and reloads context, not raw tokens per second.

Why this approach

Off the shelf cloud inference is fast to set up but sends everything, including sensitive or proprietary data, off device. This project exists to prove that a genuinely usable local setup is achievable on a tight budget using hardware most people would consider unsuitable for the job. Mining cards not designed for this workload, a patched build, and a few soldered joints turned into a machine that runs a real model at real context length, entirely under local control. Losing a card cost capacity, not usefulness: one 8GB card still runs a model that beat an 8B competitor on the work I actually give it.
